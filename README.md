# KBO 직관가이드 챗봇 — 3차 프로젝트 데이터 수집 계획

작성 기준일: 2026-09-02 (일정: 8/31~9/17, 2.5주)
GitHub: SKNETWORKS-FAMILY-AICAMP/SKN34-3rd-5Team

역할 분배·산출물 담당자 매핑은 팀 회의 후 확정 예정. 이 문서는 "무엇을 모아야 하는지"와 "프론트엔드/DB 스택"만 정리.

## 0. 메인 컨셉 재확인
서비스의 메인 컨셉은 "경기 전후 맛집·핫플레이스까지 한 번에 계획하고 나만의 직관 코스를 만들어 공유하는 야구 여행 플랫폼"이다. 챗봇의 핵심 목적은 단순 정보 조회가 아니라, 사용자가 구단/구장/방문 시간대를 말하면 "경기 전 맛집 → 경기 관람 → 경기 후 핫플레이스"로 이어지는 직관 코스를 대화로 추천해주는 것이다.

**가장 큰 목표는 사용자가 사이트를 1회성으로 쓰고 떠나지 않고 계속 재방문하게 만드는 것**이다. 직관 코스 추천은 구단·구장·시즌 일정이 계속 바뀌기 때문에 매번 다른 조합의 코스가 나올 수 있어 반복 사용 유인이 자연스럽게 생긴다. 여기에 4차의 코스 저장·공유, 직관 기록(승률 트래커)과 연결하면 "내가 다녀온 코스", "다음에 갈 코스"를 계속 확인하러 오게 만드는 재방문 동력이 완성된다.

### 메인 기능 vs 부가 기능
- **[메인] 직관 코스 추천 (챗봇 RAG)**: 사용자가 구단/구장/시간대를 말하면 경기 전 맛집, 관람, 경기 후 핫플레이스로 이어지는 코스를 챗봇이 대화로 구성해서 추천한다. 3차에서 텍스트 기반 추천에 더해 지도 시각화(카카오맵/네이버지도 SDK)와 경로 계산(티맵)까지 앞당겨 구현하고, 코스 저장·공유(로그인 기반 영구 저장)는 4차로 남긴다.
- **[부가] 구장 정보(좌석/교통/반입규정), 선수 추천, 기초 규칙, 팀 순위, 시즌 일정, 좌석 후기, 원정 가이드**: 각각 단독 질문에도 답할 수 있고, 동시에 코스 추천 시 LLM이 참고하는 재료 데이터로도 쓰인다.

> **※ 일정 리스크**: 지도 시각화·경로 계산 API 연동을 3차로 앞당기면 2.5주 일정에 부담이 커진다. API 키 발급을 1주차에 최우선으로 신청하고, 지도/경로는 "그 세션에서 추천된 코스를 보여주기만" 하는 수준으로 범위를 좁혀서(영구 저장 없이) 구현하는 것을 권장한다.

Notion 3차 목표는 "내외부 문서 기반 RAG 질의응답 시스템 구현"이다. 매칭·예측게임·포인트·굿즈 BM, 코스 영구 저장·공유 UI는 4차 웹서비스 확장 범위지만, 지도 시각화와 경로 계산은 3차로 앞당겨 추천된 코스를 바로 지도로 보여준다. 응원가(응원문화) 관련 데이터는 저작권 이슈로 수집 범위에서 제외했고, 팀순위/TOP5 중에서는 팀 순위만 수집 대상으로 한정했다.

## 2-1. 출처별 수집 방법 상세

- **[크롤링] KBO 공식 구단정보/기록실**: requests + BeautifulSoup로 팀 코드별 URL을 순회하며 선수단 명단(이름, 포지션, 등번호, 주요 기록) 표를 파싱한다.
- **[크롤링, 제한적] KBO 팀 순위**: robots.txt로 차단된 경로이므로 초 단위 자동 수집은 하지 않는다. requests + BeautifulSoup로 순위표만 파싱하고 투수/타자 TOP5 표는 수집하지 않는다. 배치 스케줄러로 하루 1~2회(경기 종료 후)만 실행하고, on/off 플래그를 둔다.
- **[크롤링] 각 구단 홈페이지 구장 안내**: 구단마다 메뉴 URL이 달라 10개 구단 URL을 먼저 목록화한 뒤 크롤링한다. 좌석 구역도가 이미지로만 제공되는 구단은 사람이 직접 보고 텍스트로 정리한다.
- **[크롤링] yagu.today/tickets**: 좌석 등급별 가격표를 BeautifulSoup으로 파싱한다.
- **[API, 핵심] 카카오 로컬 API**: developers.kakao.com 가입 → 애플리케이션 등록 → REST API 키 발급 → 키워드 장소 검색 엔드포인트(/v2/local/search/keyword.json)에 구장 좌표+radius로 맛집/핫플 검색 → attraction_reference 테이블과 Chroma 문서로 저장.
- **[API] 네이버 검색 API(지역 검색)**: developers.naver.com 가입 → Client ID/Secret 발급 → 지역 검색 엔드포인트(/v1/search/local.json) 호출.
- **[API] 한국관광공사 TourAPI**: data.go.kr 가입 → 활용신청 → 서비스키 발급 → 지역/위치기반 관광정보 엔드포인트 호출.
- **[SDK, 핵심] 카카오맵 / 네이버 지도 JS SDK**: 각 개발자 포털에서 키 발급 → 프론트엔드 script 태그 삽입 → 코스 추천 응답에 포함된 좌표들을 지도 위에 마커로 렌더링. 3차에서 바로 사용.
- **[API, 핵심] 티맵 Open API**: openapi.sk.com 가입 → 앱키 발급 → 길찾기 엔드포인트 호출(자동차/도보/대중교통 각각) → 코스 지점 간 이동 경로·소요시간 표시. 3차에서 바로 사용.
- **[API] 네이버 Directions5**: 네이버 클라우드 플랫폼에서 서비스 신청 → Client ID/Secret 발급 후 호출. 티맵 대안.
- **[API, 보류] 카카오 모빌리티 길찾기**: 사업자 등록 필요해 신청하지 않음.

## 3. 수집 시 주의사항
- KBO 팀 순위 페이지는 robots.txt로 크롤링이 차단된 경로이므로 초 단위 연동 대신 하루 1~2회 배치 수집으로 요청 빈도를 최소화하고, 투수·타자 TOP5는 수집하지 않는다.
- 구단마다 홈페이지 정보 공개 수준이 달라 품질 편차 발생 가능 — 부족한 구단은 공식 SNS·공지사항으로 보완하고 출처·최종 갱신일 표기
- 모든 문서에 고유 ID 부여(추후 추가/수정/삭제/재인덱싱 대비), metadata에 최소 `source`, `team`, `stadium`, `category`, `updated_at` 포함
- 카카오/네이버/티맵/공공데이터포털 API 키는 심사·발급에 며칠 걸릴 수 있으므로 **1주차에 최우선으로** 신청 (카카오 로컬 API, 카카오맵/네이버지도 SDK, 티맵 모두 3차 메인 기능에 바로 필요)

## 4. 수집 우선순위 (1주차 목표)
1. **구장 기본정보(좌표 포함) + 맛집·핫플레이스(카카오 로컬 API)** — 메인 기능(코스 추천)의 핵심 재료라 최우선
2. **지도/경로 API 키 발급** (카카오맵, 네이버지도, 티맵) — 3차로 앞당겨졌으니 심사 대기시간 감안해 최우선 신청
3. 좌석/교통/반입규정 (10개 구단) — 부가 기능이지만 코스 추천 시 참고자료로도 쓰임
4. 주요 선수 정보 (10개 구단)
5. 기초 규칙 요약본 (공통 문서 1개)
6. 팀 순위, 시즌일정, 좌석후기, 원정가이드 — 2주차 병행 가능

## 5. 프론트엔드 스택 결정
- Streamlit 프로토타입 단계는 사용하지 않는다. 처음부터 React로 간다.
- 빌드 툴체인(CRA/Vite) 없이 순수 `<script>` + `.html` 방식으로 React를 붙인다 — HTML 파일에 React/ReactDOM(UMD 빌드)을 CDN `<script>`로 로드하고, 같은 파일 또는 별도 `.js`에 컴포넌트 코드를 작성하는 구조.
- 백엔드(Django REST, `/api/chat` 등)는 원래 계획대로 그대로 두고, 이 React 화면이 `fetch`/`axios`로 API를 직접 호출하는 구조로 프로토타입을 만든다.
- 코스 추천 응답에는 텍스트 코스와 함께 각 지점의 좌표(위도/경도)를 JSON으로 함께 내려줘서, React 화면이 카카오맵/네이버지도 SDK로 바로 마커를 그릴 수 있게 한다.
- 개발 순서는 (1) Django API(RAG 질의응답 엔드포인트) 먼저 동작 확인 → (2) 같은 API를 호출하는 React 채팅 UI(script+html) 붙이기 → (3) 지도 SDK/티맵 연동 순서로 진행하면 된다.

## 6. DB 스택 결정: MySQL + Chroma (Neo4j 사용 안 함)

- **Chroma (벡터DB)**: 의미 기반 유사도 검색 전용. 구장 설명, 선수 소개, 반입 규정, 맛집/핫플 소개처럼 자연어로 된 비정형 안내 텍스트를 임베딩해 RAG로 검색한다.
- **MySQL (관계형DB)**: 팀 순위, 직관 기록, 좌석 후기 평점처럼 값이 정확히 맞아야 하는 정형 데이터를 저장·조회한다. 기존 기획안은 PostgreSQL이었지만 팀에서 MySQL 경험이 많아 MySQL로 대체 — Django ORM이 둘 다 지원해서 설정만 바꾸면 되고 스키마는 그대로 재사용 가능하다.
- **Neo4j는 쓰지 않는다**: 그래프 탐색이 필요한 GraphRAG를 할 때만 필요한데, 우리 서비스는 "구장+맛집 조합" 정도의 단순 결합형 질문이 대부분이라 불필요. Notion 가이드의 "처음부터 GraphRAG/Agentic RAG 넣지 않기" 원칙과도 일치한다.
- API 레이어(Django)가 질문 유형을 보고 두 저장소 중 어디를 조회할지 라우팅한다 (정형 데이터 질문 → MySQL 직접 조회 / 비정형 안내 질문 → Chroma RAG 검색).

> **※ 아래 ERD와 테이블 설계는 예시로 보여주기 위한 초안이다.** 실제 필드/관계는 팀 회의 결과에 따라 바뀔 수 있으니 참고용으로만 보고 확정된 내용으로 오해하지 않도록 한다. (ERD 다이어그램 이미지는 함께 전달한 PDF의 5장에 포함되어 있다.)

모든 Document(Chroma 청크)에는 최소 `id`, `source`, `team`, `stadium`, `category`, `updated_at` 메타데이터를 부여한다.

## 7. RAG 파이프라인 뼈대

인덱싱: 전처리 → Document(메타데이터) → 청킹(500~1000토큰, overlap 10~20%) → 임베딩 → Chroma persist. 최초 1회 전체 인덱싱, 트레이드/개편시만 증분.

서빙: 서버 기동시 VectorDB/Retriever/LLM 1회 초기화 후 재사용 → 질문임베딩 → Retrieve(top-k 4~5, 메타데이터 필터) → (필요시 고유명사는 Hybrid) → Context 제한(구단당 ~400토큰) → Few-shot 프롬프트 → Streaming 생성. Reranking은 검색품질 문제 확인될 때만 추가. Retrieval/LLM/Total 시간 분리 기록.

### 코스 추천 체인 (메인 기능)
1. 사용자 입력에서 구단/구장/방문 시간대 파싱 (예: "두산 경기 저녁 7시 잠실, 맛집이랑 갈만한 곳 추천해줘")
2. ① 구장 앵커 검색: stadium 테이블 or Chroma에서 구장 기본 정보(좌표 포함) Retrieve
3. ② 주변 콘텐츠 검색: 같은 구장 좌표 기준 attraction_reference(맛집/핫플) Retrieve (텍스트 chunk이거나 카카오 로컬 API 실시간 호출)
4. ①+②의 Context를 함께 Few-shot 프롬프트에 전달
5. LLM이 "경기 전 맛집 → 경기 관람 → 경기 후 핫플레이스" 순서의 코스 텍스트로 답변 생성
6. ③ 코스에 포함된 지점들의 좌표를 모아 프론트엔드에서 카카오맵/네이버지도 SDK로 마커 시각화 (3차)
7. ④ 필요시 티맵 API로 지점 간 이동 경로·소요시간 표시 (3차)
8. (4차) 이 코스를 로그인 계정에 영구 저장하고 다른 사용자와 공유하는 UI로 확장

텍스트 코스 생성까지는 별도 Agent 없이 "두 번의 Retrieve + 한 번의 Generate"로 구현 가능하다. 지도/경로 단계(6~7)는 RAG 체인이 아니라 프론트엔드에서 별도 API를 호출하는 단계이므로, 백엔드는 코스 텍스트와 함께 각 지점의 좌표만 JSON으로 내려주면 된다.

### LangChain 체인 구성 개념 요약
- Retriever = "질문(string) → 관련 문서 리스트"를 반환하는 Runnable. `vectorstore.as_retriever(search_kwargs={"k":5,"filter":{...}})`로 생성.
- LCEL로 `{"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm | StrOutputParser()` 형태로 파이프 연결.
- top-k=4~5, 메타데이터 필터, Few-shot 프롬프트, Context 길이 제한, Retrieve→Generate 단순 구조로 시작하는 이유는 각각 "정확도", "비용/속도", "디버깅 용이성"을 확보하기 위함.
